## [1.0.29] - 2026-11-24

- Trust now has a product surface. `/trust` opens a native TUI page over the same store and discovery the CLI uses: list all/untrusted/trusted/changed definitions, inspect content and the approved→current diff, mark rows, approve one or many, and revoke. `AGENTS.md` at any depth is standard project context: it loads by default in every mode, including first creation, edits, `git pull`, resume and nested scopes, and is never listed as a pending trust item or an execution authorization. Startup no longer prints definitions or a trust hint. In ordinary modes, a running `load_skill` for an untrusted skill raises a structured authorization prompt (allow once / trust this content version / deny) and the same tool call continues after the decision; allow-once never writes the store, a denial is remembered for that exact digest, and disconnected or cancelled waits refuse safely instead of hanging. FullAccess adopts gated rule and skill content captured in a session-creation baseline taken before the agent can write, without prompting or persisting a record; content edited after the baseline, and any resumed session without credible provenance, is never auto-adopted. Declarative agent definitions still require a persistent approval.
- `AGENTS.md` at any depth is standard project context. It loads by default in Auto, Restricted and Full, including first creation, an edit, `git pull`, a config change, a resume and a nested scope, and never needs a trust approval. It is context, not authority: it cannot grant permissions, change the permission mode, write, approve or revoke a trust record, or make another definition trusted; the loader still enforces the contained regular-file, UTF-8 and symlink boundary. `.leveler/instructions.md`, `.leveler/rules/*.md`, declarative agents and skills remain trust-gated. Existing `AGENTS.md` records are preserved but no longer consulted, and startup no longer prints the definition list or a trust hint.
- Skills are a first-class surface. `/skills` reads the same registry the runtime, the `$` popup and `load_skill` use, with available / disabled / untrusted / invalid states, search and filtering, a detail view with provenance and invocation flags, and durable enable/disable through `state/skills.toml` (project disables keyed by the canonical project root). A skill is invoked as `/name [args]`, or `/scope:name [args]` when its name would capture a built-in command. Each turn records which skills were indexed, selected, loaded and refused, without a body or a filesystem path. `load_skill` and explicit invocation verify the package and deliver a reference manifest; during that turn `read_file` can page a listed reference from the exact verified package, while ordinary path reads of `SKILL.md` and unbound references stay refused.
- The terminal UI uses one design system. The 28 independent pages share one modal workspace with consistent geometry, title, footer, focus, mouse routing and page-level list navigation. List pages share one row, selection and hover model; split pages adapt below their wide layout; document pages take the full available height; the output viewer windows large file-backed content; Memory and BTW keep their own surfaces with the same visual language. Completed replies offer `[Copy Markdown]` and `[Copy Text]`. Checkpoint restore after recovery shows the rolled-back conversation consistently, and a corrupt recovery snapshot no longer reads as an empty candidate.
- Runtime retirement and ownership are hardened. A Unix IPC connection that never sends a request can no longer hold graceful shutdown and idle eviction open, and a newer build waits for a legacy or busy runtime to exit safely instead of failing startup. `leveler runtime status` reports identity, build, work counts and idle-eviction state; `leveler runtime stop` retires the runtime only when no work would be interrupted. A user shell's terminal event is published only after its durable ownership token is released, so the composer cannot accept input into a session that still holds an active turn. `leveler background logs` for a hosted task reads the hosted record instead of an empty inventory tail.
- `AGENTS.md` no longer needs an approval; old records are preserved but ignored. An untrusted skill is still not loaded without a decision, but `load_skill` now raises a typed request instead of silently skipping it. Reading a skill reference through `read_file` is limited to the exact package version delivered in that turn.

## [1.0.28] - 2026-11-21

- Trusted Definition Security Model 1.0 is the formal cross-platform contract: unapproved definitions never enter the harness's authority context, and approval binds the exact content version. A skill's approval now covers `SKILL.md` plus its whole `references/` tree with a composite SHA-256; editing, adding or deleting a reference invalidates it. `load_skill` returns the verified reference text inline, and restricted file tools (including recursive search) refuse direct path reads of that content. Existing single-file skill approvals re-appear as `changed` and need one re-approval.
- The Unix runtime control socket now requires a per-runtime random access token in addition to its `0600` mode. The token is `0600` beside the socket in a `0700` directory, hidden from confined commands by Seatbelt read-denial or a bubblewrap tmpfs, and Linux additionally refuses peers outside the runtime's mount namespace. File tools refuse the control namespace. `ManageSchedule` is now trusted-local-only over TCP as well. Windows keeps its named-pipe ACL boundary; FullAccess remains the documented user-authority boundary. A runtime started by a pre-1.0.28 build does not speak that handshake, so a 1.0.28 client will not replace it atomically: let it finish its work and exit normally once, then start the new version. The client never signals it or steals the endpoint.
- Windows missing protected-path creation remains a known OS limitation under the new contract: a confined shell can still create a previously missing `AGENTS.md`/`.leveler` tree, but it is never admitted without approval and existing protected objects keep their OS fences.
- The trusted-definition control plane now fails closed in two more places. In every mode except FullAccess, `write_file`/`apply_patch` refuse the definition trust store, its lock and snapshot directory, and the executable-config trust store, even with an external-path resource grant; approval remains the `leveler trust` decision. A corrupt, future-version, or inside-project store now blocks the entire approval or revocation transaction before the config store is touched, and a store path inside the checkout is refused even when the file does not exist yet. A confined `leveler trust` can only write its per-command sandbox home, which the runtime never reads; pointing it at the host home hits the OS write boundary.
- The two load-sensitive tests in the full suite no longer use wall-clock thresholds or external shell programs: the background-start test starts the test binary itself as its long-lived process, and the concurrent-duration test uses a rendezvous between the two child streams.
- The Windows security canaries now also prove that a real Low-integrity shell cannot self-approve into the runtime store, cannot open the runtime's Medium named pipe, and cannot create a process through Task Scheduler or WMI. FullAccess remains a documented user-authority boundary.
- Project definitions are now inert until a human approves their exact bytes. This covers `AGENTS.md` at any depth, `.leveler/instructions.md`, `.leveler/rules/*.md`, declarative agents under `.leveler/agents`, and skills under `.leveler/skills` and the compatible project/user roots. `leveler trust` lists and approves the displayed SHA-256, `leveler trust show` reports new/changed/trusted, `leveler trust diff <path>` compares the approved version, and `leveler trust revoke-definition <path>` removes one record. Any edit, `git pull`, commit, runtime restart or session resume does not inherit the old approval. The store lives outside the workspace and fails closed when missing or corrupt. This does not close the Windows OS gap that still allows a confined shell to create a previously missing definition path; such a file is created but never admitted without approval.
- Windows resource grants now bind a filesystem object's stable volume/file id and creation time, resolved from an open handle. Listing and revoking grants works, a Session approval is persisted and reused through the execution layer, and a replaced object no longer matches the grant. Filesystems without persistent file ids fail closed instead of falling back to a path comparison.
- Fixed commit and branch reviews work on Windows without starting a `git` process. `git_history` and the review's fixed-object scope read loose objects and packfiles directly, verify every object hash, refuse missing objects, and keep the reviewed ancestry boundary. No hooks, filters, helpers or network are reachable from that path.
- Terminal device replies (DA1/Sixel capability answers) are separated from user input at the TUI boundary. A late, duplicated or fragmented reply can no longer enter the composer, including when it arrives between two parts of a typed command; pasted text and ordinary Unicode/IME keys are untouched.
- `/tasks` is a read-only workbench over the current session's goal, child agents, background tasks and reviews, the schedule definitions and their last runs, and every durable session in the global store. Active / Recent / All share one stable selection; Enter opens the existing Activity, Goal or Schedules page, `x` cancels a current-session task through the runtime, and `r` re-reads the snapshot sources. Global session rows are labelled with their snapshot time; live rows update in place.
- `/doctor` is now structured diagnostics shared with `leveler doctor`. Every check is a finding with a stable id, a typed status (`pass`, `warn`, `fail`, `unknown`, `not checked`, `not applicable`), observed evidence and an optional existing action. The TUI adds the live runtime, session, recovery, permission and terminal facts; the runtime supplies the shared configuration, provider, model, MCP-config and sandbox checks. `UNKNOWN` and `NOT CHECKED` are never rendered as a pass, live MCP connection state is explicitly `NOT CHECKED`/`NOT APPLICABLE`, and the page is safe while a turn runs without calling a provider. `leveler doctor --json` prints the same findings as a stable machine-readable report.
- An explicit `--deny-network` now survives Full. Full still removes prompts and CodeLeveler-imposed confinement, but it does not silently undo a run-level restriction the user typed; a backend that cannot enforce the denial fails instead of running open.
- An approval that lifts the workspace write fence now says so in the prompt, and only an action that can itself write (a command, a file mutation, an unsandboxed MCP server) lifts it. Approving a network fetch or a definition write keeps the admitted scope.
- Delegated children no longer hold `schedule_inspect` / `schedule_manage`: user-global schedules are top-level work, refused at admission even under Full.
- Shared model budgets take an atomic in-flight reservation per request. Concurrent requests can no longer both pass the same settled balance; a reservation is released only after its request row is durable, and an undeliverable row keeps the hold.
- Deleting a session refuses while a turn or background work is live. The CLI applies the same rule and the same storage cleanup (row + shell captures) as the runtime.
- Rename is presentation-only. `sessions.title` is separate from the verbatim `goal` request; the TUI `/rename`, `leveler sessions rename`, Web and Desktop show the title, and historical rows keep their previous display through a fallback.
- Archive is reversible: the Sessions page filters Active/Archived/All, `a` archives, `u` unarchives, and every client receives the archived flag. `leveler sessions delete` refuses live work instead of killing it.
- Resource grants can be listed and revoked: `leveler permissions grants [--session] [--json]` and `leveler permissions revoke-grant <id>`. Revocation is project-scoped by handle; an admitted call keeps its frozen policy.
- `/model <ref>` switches only the current session (matching Web and Desktop); `/model default <ref>` is the explicit global-default action. `/permission ask|auto|full` applies immediately. Invalid arguments are refused with usage instead of being ignored.
- Restoring a checkpoint takes a second confirmation that names the working-tree rollback. `/review report [id]` opens a durable report from the keyboard. Opening a deleted session reports an error instead of silently doing nothing.
- Large model tool output is addressable: `/output tool [call id]` opens the complete artifact the runtime saved, with a 512 MiB oldest-first quota and secret-value redaction. `/copy` (bare) copies the newest complete answer, `/copy N` the Nth; `/export` now appends a `## Tools` evidence section with call identity, status, exit code, duration and artifact references, never raw stdout.
- Web `/goal` runs the same Goal command as the TUI instead of being rejected. The dead Ctrl+M binding was removed from Help; `/model` is the reachable entry.
- Session summaries/snapshots carry additive `title`, `original_request`, `archived` fields; an older client keeps displaying `goal` and treats rows as active.

- Execution authority now matches the person's actual grant. A standing `Allow` rule or an automated reviewer no longer turns a matching call into unrestricted filesystem and network execution; it answers *whether* the call may run and keeps the profile's resource scopes. Exact-call consent still executes the approved effect, but it no longer clears an explicit `--deny-network`.
- A repository's `.leveler/config.yaml` may tighten the new-session default mode without trust, and may raise it to `full_access` only when the exact file bytes are trusted. `leveler trust` lists and records that file, and records only the digest it displayed: a file that changes while the confirmation is open is not trusted.
- Permission rules reject unknown keys instead of silently dropping a constraint (`deny_unknown_fields`), so a misspelled `write_path_glob` becomes a visible degraded rule set that asks, not a broader `Allow`. A durable path grant is not generated from an approved path containing `*` or `?`; that grant stays session-only.
- Credential-name classification compares ASCII-insensitively (`.ENV`, `SERVER.KEY`, `.SSH`), so a case-insensitive volume cannot resolve a protected name to a writable one.
- Confined shell commands cannot write `.leveler/agents` or `.leveler/skills` on macOS and Linux; the workspace layer already refused the edit tools, and the OS write fence now covers the shell path.
- On backends that cannot express a loopback-only boundary (Linux `bwrap`, Windows), a `Loopback` scope denies all network instead of failing every command with `UnsupportedNetworkScope`; it is never widened to the Internet.
- A review report is marked stale by any later change to the review's structured facts, including the Lead's own new finding or an adjudication that changes a decision; repeating an identical decision does not advance the revision. Untracked-file fingerprinting hashes symlink identity instead of reading the target, and initial project-rule loading reads through a directory capability.
- `/review` is a manual, read-only, evidence-driven review. It covers the current task's delivery, the working tree, the whole project, a session, a commit, a branch base, or explicit paths. The reviewer runs as an independent child with its own review id, budget, cancellation and durable report; `@model provider/model` selects another configured model and `/review cancel [id]` stops a running review.
- A Lead Reviewer may launch independent read-only investigations with `spawn_agent` for a complex review. Each child has its own context and inherits the reviewed object, read-only tools and permission boundary; it cannot write, run commands, choose another agent or delegate further. `report_investigation` returns structured facts, constraints, examined scope, unresolved questions, limitations and evidence references; candidate findings stay attributed to their source child. The review card and report list the investigations and their real states, and the durable review row stores the list. The review and all its investigations share one wall-clock budget: 20 minutes at the review turn, with 60 seconds reserved for settlement; the reviewer child receives the remaining 19 minutes and uses the last 3 of those for finalization.
- Review findings may carry a dimension, P0–P3 severity, confidence, evidence, impact, a fix direction and whether it was reproduced. Explorers and workers keep their existing `report_finding` shape. Reviews live in their own table and replay as conversation cards plus a report page; a review never opens a turn, settles a goal or edits source.
- A reviewer can page through the reviewed session's durable record with the read-only `session_history` tool (turns, events and tool results, messages, model requests, goals, checkpoints). The tool is bound to the reviewed session and is registered only on the review surface.
- Reviews carry a structured verdict written by `report_review`: conclusion, per-dimension coverage and limitations attributed to the environment, permissions, tool capability or scope. The runtime records the declaration; it never derives it from report prose or finding counts.
- Investigator findings are candidates until the Lead Reviewer adjudicates them with `adjudicate_finding` (`adopted`, `rejected`, `duplicate`, `unresolved`). Only the Lead's own findings and explicitly adopted candidates count as formal defects; pending candidates are counted separately, and rejected or merged candidates stay in the report as traceable history instead of inflating the defect count.
- A review's formal report is the complete body submitted through `report_review`'s `report` field. The reviewer's final chat message is stored and displayed separately and never overwrites the report; each submission is a complete revision bound to the evidence revision it saw. If an investigation settles after the submission and no revised report is submitted, the review says the report does not cover the latest evidence instead of presenting it as complete.
- A review honors the repository's existing `[limits]` token and cost caps and shares them with every investigation; a child cannot start a fresh budget. Review reads are opened through the workspace capability handle, so a path swapped between resolution and open cannot escape the reviewed workspace.
- Automatic review is retired. A legacy `agents.independent_review: required` still loads but no longer starts a review at turn, goal, commit or delivery settlement. Explicit test/eval settings and crash recovery of a review that was already unsettled are unchanged.
- macOS and Linux release archives are published as `.tar.xz`, about 40% smaller than the previous `.tar.gz`. `install.sh`, the Homebrew formula and `leveler update` fetch the xz archive; the `.tar.gz` sibling stays so a binary released before this change can still update itself, and both `install.sh` and `leveler update --version <old tag>` fall back to it for releases that predate the switch.
- The legacy Web UI and the `leveler web` / `/web` entry points are retired. The terminal UI, CLI and the desktop client remain; release archives no longer carry the web bundle.
- Daemon startup publishes the access token before the socket endpoint and writes the ready file atomically, so a client that observes readiness can connect. A startup stress gate holds the contract.
- A goal's objective is one stable identity through crash recovery and context fold. Several deliverables are treated as multi-step work, the adopted objective is rebound instead of duplicated, and the pre-dispatch crash window is covered.
- Completion evidence is matched to the argv that actually ran, including when the model cites a run by its display label. A requirement's mechanical kind is frozen once owed, new user words can lower a requirement but not silently raise it, and the terminal summary the schema promises is required.
- Model usage is recorded once per physical attempt, so a retried stream cannot double-count a request.
- A turn after a restart reads its context before acting, not only when the user explicitly resumed, and a first turn's own message is distinguished from prior work.
- The TUI adds transcript search with turn navigation, protects running work on exit, rebuilds the MCP, project settings and help pages, and neutralizes bidi overrides in search snippets.
- A cached MCP connection is dropped when its declaration changes, so an edited server entry cannot keep serving the previous process.
- The schedule manager publishes the policy values it accepts, and the Windows logon trigger is registered for the current user.
- Windows keeps a persistent execution host and shares write-root leases across CodeLeveler processes, so concurrent confined commands agree on the same write boundary.
- Private user data is stored owner-only on disk.
- On Windows, a private state directory created by an elevated process is accepted when it is owned by the token's default owner (`BUILTIN\Administrators`); the protected DACL still names the interposed user. The Execution Host previously refused to start from an elevated account.

## [1.0.27] - 2026-11-15

- Cross-session memory is on by default. An absent `[memory]` section resolves to `rollout = "active"`; `rollout = "off"` is the explicit opt-out, and `record_only` / `shadow` cover staged rollouts. Only `active` exposes memory to the model. Everything lives under `<LevelerHome>/memory/`; a workspace is identified by its git remote, and a temporary working directory has no workspace scope.
- Capture runs as durable background work after each settled turn. The extraction call uses a forced tool call and writes structured observations as Markdown files plus a SQLite ledger row; the turn itself is never blocked and committing an outcome is idempotent. A normal quit releases an in-flight job as retryable without charging the bounded retry budget, and startup scans for claimable jobs so a cancelled capture resumes without a new turn. Paused sessions and a global `off` rollout record skipped turns instead of backfilling them on re-enable.
- Dream consolidates pending observations into Markdown topics. A durable six-hour lease serializes it across processes and an owner whose PID is gone is treated as expired. Automatic Dream runs after capture settles; `/dream` runs one pass; `D` on the memory page runs a bounded batch.
- Each turn's system context can carry a bounded `## Cross-session memory` index of topic paths and one-line descriptions. The agent reads a topic with the ordinary `read_file` tool; there is no retrieval API and no vector database.
- `/memory` opens the management page (both scopes, read, filter, refresh, pause and Dream keys), and `leveler memory status|show|remember|forget` covers the CLI. Forget binds to the BLAKE3 hash printed by `memory show`: a tombstone is written before the file is removed, the path is excluded from the index, capture and consolidation, and the retained archive is invisible to the agent's file tools.
- A `blocked` goal resolution is refused once while the model's own latest explicit plan still lists steps it never marked completed. The refusal names the open steps and structured exits; a confirmed block is accepted with the conflict kept in its receipt. The check is bounded once per drive, never rewrites a block into a completion, and never completes pending steps on the model's behalf.
- `shell_command` names input mistakes instead of ignoring them: `program`, `args` or `command` used beside or instead of `cmd` and a wrong-typed `cmd` are refused by the schema, and a refused call never executes. `reason` and the documented `workdir` alias keep working.
- Plan progress has a dedicated TUI status row and updates in place.
- Sub-agent run futures are boxed, so nesting no longer adds a full stack frame per level.
- A completion claim the runtime refused for a named reason is recorded with that detail and is not booked as a runtime gate failure in evaluation.
- Dependencies: `quinn-udp` 0.5.16 closes RUSTSEC-2026-0538. Added GitHub issue forms.
- Background execution mutation accounting is path-independent. A task's settlement change set is part of its durable terminal fact and advances the workspace version once per execution, whether the result arrives through the auto-delivered notice, `wait_task`, or `get_task`; previously only an active read counted the task's own writes, so an auto-delivered result could leave an older pass looking current. A failed or stopped task that changed files still counts; a task that changed nothing adds no mutation; repeated reads cannot advance the version twice. A completion attempt also diffs a still-running write-capable task against its own launch baseline, so a write the task has already made is observed before old evidence is accepted — a real diff, not a blanket "running tasks wrote" rule. Unknown change sets (no baseline, failed diff) stay unknown rather than becoming "unchanged".
- Background verification is bound to the workspace version it actually ran on. The runtime samples the mutation counter at the real execution boundary (right before dispatch) and again when the execution ends, and records both on a durable `CommandExecutionVersions` row. A passing run counts only when its start and end versions are equal and at least the completion's version; a background test that exited 0 while the model kept editing is a real success but not evidence for the current tree, and the gate refuses it with the command, execution id, both versions and the current version. A rerun on one version completes normally. Legacy runs written before start versions were captured keep their real exit status and cannot claim consistency. This is a version check over the runtime's observed mutations, not a filesystem monitor.
- Completion verification now has an explicit evidence policy per requirement kind. A `named` deliverable is model judgement: a delivered `done` account is recorded as `reported` and completes normally, with no "no mechanical check" warning. A passing recorded run of a declared `tests`/`command` satisfies it only when that run is the exact declared command and is the newest matching execution; a different or compound line is not its record. For `tests`, `verified` is the declared command contract — the line ran and exited 0 after the last change — not a claim that the command executed tests. Requirements that need evidence the runtime cannot obtain stay `unverified` and keep their warning.
- Memory is on by default: an absent `[memory]` section resolves to `rollout = "active"`, and `rollout = "off"` is the explicit opt-out. Docs, CLI status and the TUI empty state follow the resolved rollout.
- Editing `[memory]` is a live configuration change. The config diff now classifies `memory` / `memory_model` as real dimensions, and a reload publishes the freshly parsed bundle instead of the previous one — a memory-only edit can no longer be mistaken for a comment and freeze the boot-time rollout (previously `/memory` kept reporting "not enabled" until the process restarted).
- `/memory` opens as a centered overlay over the conversation: Global and Workspace grouped in one list, a live Markdown preview, search, `Ctrl+F` fullscreen, and the existing management keys. The off state names the config file the runtime actually loaded instead of a hard-coded path.
- Background task display: starting a task no longer posts a second notice next to the tool row, and a failed task is a record in the conversation and the jobs page instead of a footer reminder that needs acknowledging. The running-count cell counts only tasks that are running now.
- Windows child-process output is decoded incrementally: a multi-byte character split across pipe reads stays one character, background logs use the same decoder, and a truncated GBK result no longer turns its retained head into replacement glyphs. The TUI full-output pager prefers the UTF-8 presentation copy beside the raw capture; the raw stdout/stderr capture files remain byte-exact.
- A user shell that fails before it spawns (for example an Assisted command on a Windows host without `leveler-confine.exe`) shows the host's refusal in the live view, not only in the reconnected record.

## [1.0.26] - 2026-11-12

- Continuation, pause, amendment, cancellation and questions are decided by the model in the running turn, not by a wording pattern. The model declares the meaning with `declare_intent`, quoting the newest user message verbatim; the runtime checks that the quote really came from that message, which goal it targets (and refuses to guess when several are running and none is named), the legal ordered operations, and the plan step a boundary names by stable id. Any language, phrasing or compound instruction ("继续执行，但第三阶段完成后暂停") uses the same path, and no extra classification call is made.
- A pause is released only by a validated `continue_task`. Clients submit the user's text unchanged and project the runtime's goal state; "继续" no longer turns into a special client-side resume intent. A supplement or a status question neither releases a pause nor starts work, and a declaration cannot create authority the user did not state.
- Accepted declarations are stored in order with the turn that carried the quoted user message (migrations 0053, 0054), so a restart can still answer who authorized what, with which words. A turn that continues the same goal reuses its plan instead of re-planning the completed stages from nothing.
- A clarification is durable. Each request has an id, structured questions and an answered/skipped/cancelled terminal in the event log; the live waiter is only a delivery channel. A client disconnect, a daemon restart or a task cancellation no longer discards the question or lets a late answer start cancelled work, the first terminal wins, duplicate or stale answers are refused, and the TUI restores the pending card from durable state.
- A checkpoint carries the last window's answered clarifications, amendments, verbatim user messages, runtime-observed command outcomes and accepted outcome. The plan is projected from the newest declaration, so a yielded window does not repeat work its predecessor finished, and a yielded turn is shown as a neutral boundary rather than a failure.
- `docs/INTENT_CONTRACT.md` records the ownership boundaries for the declaration, validation, persistence and client projection.
- Goal scope is a structured, model-declared requirement set. `commit_task.requirements` seeds it for a Chat-committed task and `declare_scope` adds, amends, replaces, waives or restores requirements on an already bound goal; every operation is anchored to a verbatim quote from the newest user message. The runtime validates the quote's existence, requirement identity, legal transitions and event order, and never re-reads the objective's prose. The keyword, negation-word, section-heading, quantifier and test-name heuristics are gone, so "特别优化启动速度", "更新 specification 文档", "能不能加一个 status 字段？" and `## Abnahmekriterien` are ordinary user text that only the model interprets.
- The completion gate holds a model to its recorded set: every active deliverable is accounted for by stable id, artifacts and absent artifacts are checked against the workspace, content literals against the target file (`content` requirements put the exact literal line in `text`), commands and test runs against the recorded execution history after the last change. A resumed or compacted context cannot shrink the set, and a requirement reported done without a mechanical check is surfaced as an explicit unverified boundary rather than silently accepted as proof.
- Requirement changes are durable ordered events (migration 0055) carrying the authorizing turn and the verbatim quote; the current set is a fold of that history. `get_goal_scope` projects the set and its change history, and Goal mode states the declaration obligation in its contract.
- `docs/GOAL_SCOPE.md` records the requirement ownership, declaration, validation, history and completion-gate boundaries.
- Declaration and evidence are separate. `update_goal(verification)` stays the model's declaration; the gate resolves its citation against the runtime's own execution record by call id, exact command line, or command plus a trailing note. A failed run, a run that predates the last change, or one a later run of the same command contradicts is refused for that exact reason. No command is classified by name or output, so an unfamiliar runner counts exactly like a familiar one when the record proves it passed.
- An accepted completion persists a structured `VerificationReport` on the task terminal: an aggregate Verified/Unverified verdict plus one record per owed requirement carrying its id, kind, state, the execution's call id, command, exit code, workspace version and model step. Verified, CompletedUnverified, Incomplete and Blocked are projections of the task outcome, this report and the stop reason; an unverified completion is delivered with a warning instead of being held for user confirmation.
- A terminal recorded before the structured report still replays: the removed host-owned verdict string in the same field reads as "no report", while a malformed report still fails replay instead of silently becoming unverified.
- The remaining runner-name and output-marker vocabulary (`is_verification_command`, `names_a_test_suite`, `reports_no_tests`) is gone: the runtime no longer reads a command's name or sniffs a suite's output to decide what its result means.
- A completion is never `Verified` without a requirement-level record. With no owed requirement a cited command can still account for the completion, but the terminal is unverified: a passing command proves an execution, not a delivered requirement. The earlier empty `Verified` report claimed coverage the runtime never established.
- `tests` requirements declare their exact command in `target`. The runtime matches recorded runs of that command — custom commands work, no runner vocabulary is involved — and refuses a failed, stale or never-run declaration. Because no structured test result exists, a passing command is reported as unverified test coverage with its call id, command and exit code, so `echo`/`true` can never satisfy a tests requirement as verified coverage. Legacy `tests` requirements recorded without a target stay finishable at the explicit unverified boundary.
- A pause boundary is reached only by an explicit `completed` status on its step. A step that was deleted, renamed without its stable id, replaced, split or merged is still outstanding; the model may adjust the plan freely and re-declare the boundary when the stage really moved.
- A goal-lifetime background task whose runtime generation was killed is no longer adopted by its replacement. The Execution Host records the admitting boot at spawn and accepts an idempotent owner-loss fact (protocol minor 2, optional `process.owner-loss`); the replacement records it only after the boot lease proves that generation dead. The task is projected as Lost while the host keeps the process and its output, its elapsed time stops at the proven loss, and `leveler background list` names the runtime as its owner. The host never signals the process, repeated restarts keep one record and one timestamp, and graceful shutdown kills only the current generation's goal work.
- A detached command whose owning runtime is gone now settles its TUI row as state unknown instead of keeping a running clock; the same applies to the runtime's unknown background-task terminal. The Desktop jobs list settles a vanished row from its durable record (Lost, Unknown, Conflict, Completed, Failed or Cancelled) and never keeps it as running without proof. A newly opened Desktop window restores durable Lost/Unknown rows, and its labels keep an unprovable outcome distinct from a failure.
- A failed Execution Host startup reports the host's own stderr tail, so the readiness error names the cause instead of only an exit status.
- Transient provider failures no longer end the whole request. `[retry]` is a route fact (`max_retries`, `recovery_seconds`) defaulting to 12 retries inside a 600 s window; backoff climbs to a 60 s steady rate, every wait is checked against the remaining window, and `Retry-After` wins. A retry after a tool result does not repeat the side effect, and the TUI says "model service unavailable · retry" instead of reporting a lost connection.
- Project rules are read once per turn and delivered with a typed audit. Unreadable, invalid-UTF-8, non-file and symlink-escaping sources are reported instead of silently dropped; empty, absent and loaded sources stay distinguishable; a mutating call pauses when an applicable scoped rule cannot be read; a directory's own `AGENTS.md` is scoped to it.
- Tabs and control bytes are normalized at the composer and Markdown boundaries before width measurement, so pasted input, history and model Markdown cannot ghost later cells. The splash deletes its Kitty image data by id before leaving the alternate screen.
- The standalone Flutter mobile client, its relay, and the host-side remote protocol/agent crates that only served it are removed. The CLI and TUI no longer have paired-device commands or screens; the local transport, runtime host and client command/event/snapshot protocol remain the native session interface for other clients.
- Dependencies: `rmcp` 3.9.0 closes RUSTSEC-2026-0462; `cap-primitives` 4.0.3 closes the sandbox escape in RUSTSEC-2026-0482; `rustix` 1.1.6 closes RUSTSEC-2026-0486. RUSTSEC-2026-0459 (bundled SQLite in `libsqlite3-sys`) has no fixed `sqlx` 0.8 release, so it is recorded with an expiry and a local-file reachability boundary instead of being silently ignored.

Secrets are classified by value instead of by field name, so PEM blocks, `DB_PASS`, JSON/YAML credentials and `Authorization` values are redacted while code identifiers, prose and JSON keys stay byte-identical; a placeholder can no longer be written back to disk through `write_file`, an added file or a new patch line.

## [1.0.24] - 2026-11-07

- Durable scheduled automation. `leveler schedule add` stores a definition in `~/.leveler/state/schedules.db` with one workspace, one action, one trigger and its policies. Actions are a shell command, a typed native action, or an agent goal. Triggers are a one-off RFC 3339 instant, a fixed interval, a daily time, selected weekdays, or a five-field cron expression in an IANA timezone. Session policy is `continue` or `fresh`; overlap is `skip-if-running`, `queue-one` or `allow-concurrent` (`allow-concurrent` requires `fresh`); a missed slot is `skip` or `run-once` within a grace window. Runs are claimed under a renewable lease, and an expired lease settles `unknown` instead of retrying. `list`, `show`, `update`, `grant`, `revoke-grant`, `runs`, `pause`, `resume`, `run-now`, `cancel` and `remove` manage the definition; `dispatch` runs one pass and `serve` is the resident dispatcher. The TUI `/schedules` page, the Web UI and the desktop Automation page use the same runtime facts, and the model-facing `schedule_inspect` / `schedule_manage` tools manage the same definitions without creating a second authority.
- Unattended grants. A native or agent action (and a shell run) needs a persisted grant covering its action, workspace, trigger, permission mode and external-side-effect choice. Editing a covered field invalidates the grant; Full permission does not substitute for it; a missing grant refuses the run before it starts.
- Operating-system wakeups. `leveler schedule enable` registers a launchd agent on macOS or a per-user Task Scheduler task on Windows; `disable` and `uninstall` remove it; `status`, `wakeups` and `doctor` report the registration, wake history and checks. Linux reports the wakeup backend as unsupported; schedules remain runnable through `serve` or `dispatch`.
- Deterministic native actions. `leveler native capabilities` probes Mail on macOS or Outlook on Windows without launching the application or requesting consent. `leveler native action` runs `mail.draft.create`, `mail.send.open_ui`, `mail.send.submit` and `mail.sent.check` with no model, daemon or session; input is validated before planning, user text travels through private `0600` files, and success requires a recognized result marker. A timeout or unrecognized outcome is `unknown` and is never retried. The `native_capabilities`, `native_action` and `native_verify` tools expose the same contract to the model.
- Computer use. `computer_observe` and `computer_act` implement desktop observation and control over macOS Accessibility/CoreGraphics and Windows UI Automation/Win32. Observation references are per session and revalidated against the live UI before each action. The tools reuse the existing approval policy, capability packs and image channel; there is no separate execution path. macOS reports Accessibility and Screen Recording permission at call time.
- Foreign session continuation. `/resume-claude` and `/resume-codex` discover local Claude Code and Codex sessions, enforce a workspace match, and import one into a native session seeded with a bounded briefing. The source store stays read-only and authoritative; tool calls are not replayed, a completion claim from the source remains unverified, and `foreign_session_history` reads the original transcript on demand.
- Durable input and delivery. Session input journal migrations 0049–0051 give each submission an identity before admission, so a reconnect or recovery delivers it once instead of losing or duplicating it. A final answer is bound to the model's explicit `deliver_answer` declaration and persisted as a durable event before the turn terminal; a crash after the answer is recovered without another model call.
- Unified TUI syntax highlighting and diff rendering: one highlighter for code blocks and diffs, and an applied diff remains one copyable document. `diff_visual_acceptance.py` renders the diff corpus for visual acceptance.
- A client that loses the runtime startup race adopts the live runtime instead of failing permanently.
- Natural recurring schedules keep the rule's own grid while a shell run is active; `allow-concurrent` shell runs use one execution context per run; a one-off keeps its pending occurrence when its trigger is rescheduled; `schedule show` only projects a pending occurrence.
- The headless CLI prints the committed delivery rather than text from a bookkeeping round, and continuation observers replay the accepted answer without persisting a second delivery fact.
- Regenerated the protocol schemas and Web UI types, silenced vendored crossterm lints, fixed platform-gated clippy errors, and kept reconnect test fixtures isolated on Unix.

## [1.0.22] - 2026-11-04

- Streamable HTTP MCP. `[[mcp_servers]]` accepts `url` (and optional `transport = "streamable_http"`, `headers`, `bearer_token_env`) in addition to the existing stdio `command` / `args` / `env` form. Header and bearer values are environment-variable names. The client negotiates MCP `2026-07-28` and falls back through the Streamable HTTP versions still used by older servers. A tool call whose result is unknown after a timeout or a dropped session is not sent again. OAuth 2.1 is not implemented. Existing stdio servers keep working without a config change.

- An empty conversation opens on a welcome card: the brand mark, the tagline, a rotating tip that names `/goal`, `/diff`, `/context` and `/theme`, and clickable entries for session history, help and model selection. It disappears as soon as the conversation has real content, folds to a narrow layout on small terminals, and paints the original mascot where the terminal supports a native image protocol.

- Retired Memory 2.0: removed background extraction, storage/retrieval, context injection, tools, commands and management screens. Session history, resume, compaction, goals, plans and project rules remain available. Existing databases remove retired queues and policy columns on upgrade.

- A user-stated pause is now an execution boundary, not an unresolved plan. "Finish stage 1, then wait for my confirmation" ends the turn normally with stage 2 still `pending`; the harness does not buy extra rounds to pressure past it. The boundary is read from the user's own words and the model's plan, requires the named stage to be completed, survives resume/compaction, and is released by a later user instruction. A model's own claim that it needs confirmation is still not a pause: without an explicit user boundary, the open plan keeps its normal continuation.
- Plan progress counts only the current plan. A step the model replaced is recorded as `abandoned` history (shown separately, e.g. `计划 1/2 · 1 项历史步骤已弃用`) instead of inflating the denominator; it is never counted as completed. An explicit user pause is shown as `等待用户确认` rather than an unexplained open plan. That label now comes from the goal the runtime recorded the pause on, so an earlier goal's pause never marks a different goal as waiting, and a paused Chat-committed goal keeps its own badge while an ordinary follow-up question is answered.
- A request keeps its authority in question form. "能不能顺便把 X 也补上？" and "Can you also add X?" now add `X` to the goal's scope instead of being discarded with every other question; status queries ("测试通过了吗？"), consultations ("如果加 X 会有什么影响？") and authorization changes ("能不能先不要执行阶段 2？") still change no requirement. Asking a question never releases a pause the user set, and changing scope never releases it either.
- `commit_task` and `spawn_agent` are no longer described with the same word. Committing a goal is not delegation: the row says `Goal committed`, `Goal not committed` (a refused acceptance list, with the reason one fold away) or `Goal commit failed` (a real tool failure), while only `spawn_agent` says `Delegation`. Both the conversation and the Tools screen read one status mark, so a refused declaration is a warning everywhere instead of a red failure in one view.
- A chat turn that ends while the plan it published is still open no longer just stops. The runtime states the open steps and the three honest ways out — continue the work, rewrite the plan because a step is no longer needed, or say what blocks it — bounded by the same no-progress guard as a Goal continuation, and never as a success claim. A completed plan, a host-seeded plan, an ordinary question and a denied permission all buy no extra round; a Goal turn keeps its own continuation. The plan stays the model's declaration: the runtime does not mark steps done, does not require 100%, and does not treat a full plan as proof.
- Removed the `/develop` command and its fixed Analyze → Coding → Review workflow. `/goal` remains the explicit-goal entry point; model planning, review, delegation and goal verification are unchanged.
- Configuration is live state: editing `~/.leveler/config.toml` (or the repository bundle) applies to the next turn without restarting, and `/reload` re-reads it immediately. A running turn keeps the model/provider/generation it started with; a session created without naming a model follows the new default, while an explicit `/model` choice stays pinned. Invalid or partially written files keep the last working configuration; a failed reload names why. Settings that only apply at start-up (UI language, browser product) are reported as requiring a restart instead of being reported as applied. MCP servers are reconciled per server, so unchanged connections survive a reload.
- `/context` and the new `/usage` are now one "Context & Usage" page: `/context` positions it at the context section, `/usage` at the usage section. Usage comes from the runtime's durable model-call ledger and covers this turn, this session, today, the last 7 days, the last 30 days and all time, with per-model token and metered-cost detail.
- Usage keeps "unmeasured" apart from "zero": a provider that reported no usage, a model with no configured price, and a partially priced scope are shown as unknown or as a known part — never as `$0.00`.
- Fixed read-only diagnostics during a running turn: `/trace`, `/context` and `/usage` open immediately while the agent works, read the same runtime state, and coalesce event-driven refreshes into a single query so answers are no longer discarded.
- The context page no longer prints a separate `Free` detail row; remaining capacity stays in the occupancy map and the header ratio.
- Fixed a buffer overrun that crashed the `/` command menu on narrow terminals (40 columns and below).
- A background task that reaches its terminal state while the user steers still delivers both the exit and the message. Undelivered task facts drain on the next admission, a failed provider attempt retries the request that already holds the fact, compaction keeps the delivered task identities, and concurrent terminal writes stay gapless.
- Fixed a background task started with the default `goal` lifetime inside a plain chat session outliving its turn. The turn's terminal is the boundary that lifetime promises, so the task is stopped there; a goal that still owes work keeps its services.
- A runtime of a different build is never attached while it is busy: a client that finds the endpoint busy defers its upgrade instead of silently joining the previous generation. An active background task now states its own lifetime, so quitting the TUI stops goal-scoped work while a shell the user sent to the background keeps running.
