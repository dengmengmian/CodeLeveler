一句话结论

第一档

请求批准 = 旧 Auto

保留工作区写沙箱、危险命令/MCP/外部写审批、Session/Project 授权。普通开发 0 审批。

第二档

替我审批 = 新 Auto

默认自主执行；只在当前调用可直接识别出不可恢复破坏时请求批准。无工作区写围栏。

第三档

完全访问 = 不变

无 CodeLeveler 审批与沙箱限制；显式 --deny-network 仍生效。

内部不是三档，而是「契约 × 档位」

用户界面仍然只有三档。契约版本只作为 Session 的内部事实与兼容标记。

新 Auto 怎么判断

1
显式配置优先用户 deny / ask 规则、pre-hook、只读角色、所有权拒绝。规则永远先于自主判断。
2
工具声明的具体副作用定义写入需真人；邮件发送、桌面控制、私有网络、其他执行者的任务按工具自己的 admission。
3
不可逆检测（唯一新增的 Ask 来源）删除真实数据、磁盘销毁、数据库/卷删除、Git 历史丢失、MCP destructiveHint。只看当前调用的结构化 argv/AST/effects。
4
独立边界已存凭据使用、凭据库读取、sudo、私有网络。这些不是不可逆损失，但属于不能由 Auto 自主绕过的资源/OS 边界。
5
边界无法强制 → 明确失败Windows 断网命令、Linux 无 user namespace、不可表达的 Loopback。返回 ExecutionBoundaryFailure，不假装允许。
6
其余 → 自动执行未知程序、复杂 Shell、python script.py、npm run build、普通 Git、普通网络、普通 MCP。

python script.py 为什么不审批：运行时只解析当前调用的 argv，不读取脚本、不分析依赖、不追踪子进程。 脚本内部可能删除文件、访问网络，但那是用户选择 Auto 时接受的风险。运行时不会因为「无法证明完全安全」而询问。

新 Auto 如何避免变成 Full

新 Auto 去掉的

普通写入的工作区路径围栏。只有这样，工作区外的普通写入才可能真正成功，而不是「策略允许、沙箱拒绝」。

新 Auto 保留的

显式规则与 hook、凭据边界、私有网络、sudo、定义写入同意、信任闸门、子 Agent 所有权、不可逆检测、OS 权限。

Full 去掉的

全部准入判定：规则、hook、所有权、凭据、定义同意、不可逆检测。只有显式 --deny-network 仍保留。

诚实的限制

新 Auto 不保证发现所有不可逆行为。脚本、make clean、MCP 服务器谎报 annotations 都是文档化缺口。

历史兼容：不静默提权

  • 数据库迁移只加 permission_contract 列，旧行一律 V1；不重写历史 mode。
  • 恢复旧 Session 时按行内契约运行；切换档位不改变契约。
  • 采纳 V2 必须显式确认，并同时写入 (mode, contract)；待审批问题先 supersede。
  • 项目配置缺省视为 V1；新项目模板写 V2。
  • 调度授权绑定 (mode, contract)，旧 v3 授权 fail closed。
  • eval 固定 V1，避免新 Auto 的无写围栏破坏 eval 封闭性。
  • 回滚到旧二进制只会更严，不会放大权限。
