# CodeLeveler 架构与使用说明

[English](ARCHITECTURE.md) · [自定义 Agent](AGENT_EXTENSIBILITY.zh-CN.md)

CodeLeveler 让 AI 模型在真实工作环境里完成任务。你可以提出目标，让它读取和搜索文件、执行命令、修改代码，并通过界面了解过程和结果。模型决定怎样工作；程序负责把调用真正执行、保存记录，并处理权限、取消和恢复。

> **Harness 是模型能力的放大器，而不是限制器。**
>
> **模型决定能力的可能性，Harness 决定这些能力能在多大程度上得到发挥。**

CodeLeveler 的首要目标是尽可能释放每个模型自身的最大能力，不追求缩小模型间的能力差距，也不要求其表现趋同。Harness 提供可靠的上下文、工具、执行环境与反馈，帮助模型充分推理、探索和自主执行；必要的安全、权限与宿主执行权威边界仍然有效。

编程是当前第一个产品方向。底层运行基础也面向评审、研究等其他智能体。增加这些领域时，共用已有的任务、权限和持久化机制，各自定义工作规则。

本文前半部分说明用户会遇到的行为，后半部分说明架构责任划分和产品契约。它与英文架构文档表达同一套契约，中文按使用过程组织。

## 1. 可以从哪些地方使用

| 使用方式 | 入口与当前范围 |
| --- | --- |
| 命令行 | `leveler` |
| 终端界面（TUI） | `leveler tui` |
| Web | `leveler web` |
| 移动端 | `apps/leveler-mobile`（源码预览） |
| 远程宿主桥 | `leveler remote` 与 `services/leveler-relay` |

独立桌面应用和云端 Worker 尚未发布。这些客户端使用同一套运行时和业务协议。客户端可以位于其他机器上；“同一套运行时”也不要求所有项目共用一个后台进程。

### 选择项目或无工作区会话

项目会话有一个主要工作区，可以使用该项目的配置、规则、技能和相关能力。无工作区（No Workspace）会话没有关联目录，也不会偷偷使用 HOME、启动目录、上次项目或内部临时目录代替。

无工作区会话使用同一套运行时，但不加载项目配置和规则、自动执行钩子、技能、项目外部工具连接、Git 与代码分析、文件恢复点或命令环境。默认需要工作区的工具会拒绝调用，即使使用 Full 权限或传入 HOME 的绝对路径也如此。这属于缺少工具所需资源。

全局历史汇总已有项目与无工作区的持久记录。项目目录丢失时，历史保留并标记工作区不可用；某个来源读取失败时，返回其余结果并说明缺项。全局扫描不创建或迁移数据库，不启动后台进程，也不建立另一份任务记录，并且只开放给可信本地客户端。

## 2. 一次工作怎样进行

以用户要求“修复这个缺陷并验证”为例，实际过程如下。

| 步骤 | 负责方 | 发生什么 |
| --- | --- | --- |
| 1 | 客户端 | 接收目标，交给编程领域规则 |
| 2 | 领域层 | 提供仓库约束、工具说明与完成要求 |
| 3 | 运行时 | 建立任务与回合，持久保存输入，管理预算、事件、取消和恢复 |
| 4 | 模型 | 理解目标，调查代码，决定下一步，通过工具发起调用 |
| 5 | 能力 | 执行读取、搜索、命令等工作；涉及真实副作用时经过宿主执行边界 |
| 6 | 运行时 | 保存实际结果，例如退出码、文件变化和产物 |
| 7 | 模型 | 结合目标和证据判断是否继续或完成 |
| 8 | 客户端与用户 | 展示过程与结果，用户决定是否接受交付 |

模型看到的工具会按需要加载。每个新目标从基础编程工具、产品默认能力面和很小的能力控制接口开始；项目启用 memory 时，记忆工具与指导属于默认能力面，第一轮请求即可见。其他可选能力在加载后才把工具和指导带入后续请求。同一目标内已加载能力只增不减。

### 能力存在、权限允许和当前可见各有条件

| 条件 | 对用户的含义 |
| --- | --- |
| 可用（Available） | 运行环境实际具备能力，例如已配置搜索服务、PATH 中有 Git、模型支持图片、所选浏览器可驱动 |
| 允许（Permitted） | 配置、权限和操作系统隔离规则允许调用，包括记忆开关与委派权限 |
| 已暴露（Exposed） | 当前模型请求实际携带的工具 |

当前可见工具必须同时可用并被允许。加载工具不会创造能力或授予权限。模型决定需要加载什么，编程规则所在的领域适配层负责校验和加载。程序不按任务关键词、模型强弱、模型服务商或轮次擅自挑选工具。聊天、计划、目标等协作方式也不会改变执行权限。

### 工作过程中怎样说明进展

开始工作时说明目标和首步；有关键发现、阻碍或方向变化时说明影响和下一步；长时间等待时说明当前状态与等待事项。界面只显示收到的模型正文，不生成发现、不编造下一步，也不把工具活动自动解释为目标进展。

## 3. 在终端里怎样看过程和结果

对话区按事件原顺序显示用户输入、模型的进展说明、工具回执、文件修改和最终回答。

- **工具组默认收起**：连续同段的读取、搜索、列目录、执行命令和外部工具调用合为一组，标题累计真实种类与次数，失败仍计入种类并单独标记。后台启动调用返回成功只说明启动调用已返回，不能把仍在运行的进程显示为完成。
- **失败收在入口里**：普通工具失败默认收起，展开后才显示失败目标与脱敏错误；错误来源、错误码和能否恢复保持不变。
- **diff 默认完整显示**：已确认的文件编辑独立展示文件名和修改统计。长到会淹没这一轮的 patch 在会话里做摘要，打开该行（`Ctrl+O` 或点击）显示全部行；工作区 diff 读取失败必须明确显示失败。
- **思考单独一行**：思考进行中显示 `◆ 思考中…`，结束后离开对话，但原始记录和协议要求的历史回传不受影响。
- **本地命令（Shell Mode）**：空输入框里输入 `!` 进入 Shell Mode，`!` 只是模式标记。补全完全离线，覆盖文件、目录和 PATH 可执行文件，接受候选从不执行命令。每次执行只有一条内联记录，显示真实状态、stdout/stderr 来源和完整命令；完整输出在 TUI 内单独打开。
- **滚动与状态栏**：有内容的对话从视口顶部开始，跟随末尾行为正常。状态栏的上下文占用按运行时预计输入量除以完整模型窗口显示；只有没有运行时快照时才使用模型服务报告的用量，窗口未知时不伪造占用。

| 操作 | 结果 |
| --- | --- |
| 点击工具组标题 | 展开或收起成员 |
| 点击成员或失败条目入口 | 查看其具体详情 |
| Ctrl+O | 展开最新执行（工具组或用命令）的详情 |
| Ctrl+G | 跳到最终回答；没有最终回答时仅提示 |

复制文本区分“已发送”与“已验证”：只有本机非 tmux 的原生剪贴板写入且读回一致才标记已验证。SSH 与 tmux 跳过原生路径，只表示已发送。程序不会为复制静默修改 tmux 配置。

## 4. 权限决定哪些动作能执行

权限模式（Permission Mode）描述 CodeLeveler 产品运行时的权限。它不替代用户对具体开发、部署或数据操作的授权。精确执行契约见[§9.0](#90-permission-mode-顶层产品契约)。

| 模式 | 用户会遇到的行为 |
| --- | --- |
| Full（`FullAccess`） | 已实现能力完全放开，CodeLeveler 不因权限或操作系统隔离询问、拒绝或限制，审批次数为 0 |
| Auto（`Assisted`） | 普通开发默认允许，包括全部 Git 操作，以及工作区内字面路径的 `rm` / `rmdir`；只在删除、提权，以及凭据、工作区外写入、会执行本地程序的 Git 配置上要求批准 |
| Restricted（`RequestApproval`） | 按目的地和资源边界执行，无法可靠约束的范围明确询问、拒绝或标记不支持（Unsupported） |

Full 下能力缺失、参数错误、操作系统或外部服务失败仍会如实报错；取消、超时和资源回收照常有效。Auto 的批准只覆盖当前明确动作：执行时沿用同一批准，不再次拒绝，也不扩大之后未批准的调用。操作系统隔离不能比已允许的权限更严。

### 批准一次、会话或项目的区别

Once 只批准当前调用，不保存为可复用记录。Session 绑定真实持久会话，Project 绑定真实项目对象。复用必须重新解析和校验资源，文件、代码仓库、远端目标或凭据改变后，旧记录不能继续代替新批准。文件批准绑定精确路径与实际对象，新文件绑定现有父目录，不能靠目录前缀放大范围。

读写、删除、远端读写、后台观察与控制、凭据使用与读取明文都是不同能力。批准使用凭据不自动允许读取凭据文件或访问网络。授权界面只展示宿主解析的请求，模型描述和界面状态不能生成执行权限。

### 浏览器和搜索分别启用

浏览器控制与网页搜索独立配置，互不替代。缺少搜索服务的密钥不会改用浏览器搜索，浏览器失败也不会转用搜索。

浏览器控制分别提供导航与标签页、像用户一样操作、观察这三个工具。自动化浏览器会话不等于接管用户已有窗口；Safari 自动化使用与普通浏览数据隔离的独立窗口。浏览器在会话开始前按调用指定、配置默认、本机自动化默认的顺序选择，Safari 必须显式指定或配置；指定产品无法驱动时明确报错。

## 5. 怎样判断回答和任务是否结束

命令成功、测试通过、文件变化和模型说“完成了”，分别提供不同证据。运行时记录可确定的执行事实，模型结合领域规则解释证据，用户拥有最终验收权。模型不能通过缩小自己声明的验收范围来宣布用户委托的整体任务完成。

最后一段正文结束后，任务进入收尾（`Finalizing`），还可能需要依赖结算、必需评审和结果裁决。只有运行时持久保存的任务结束记录（`TaskFinished`）才能确认已结束。没有提交终态时，界面只能显示可恢复错误，不能自行合成失败或完成。

| 结果或状态 | 能证明什么 |
| --- | --- |
| 已回答（`Answered`） | 已回答，修改文件不会自动将其升级为完成 |
| 声明完成（`Completed`） | 模型声明目标已完成，仍需实际验证 |
| 未能继续推进（`Stalled`） | 保留原因，作为可恢复中断处理，未完成目标不结清 |
| 工具成功或最终正文 | 本次调用或输出发生过，不能替代任务终态 |

测试、编译和代码检查是普通工具。运行时不会在任务结束后另起验证计划，也不会自动生成“验证通过、失败、未运行或不可用”的状态。模型按用户要求执行验证，缺少观测时标记未知。

## 6. 断线、继续和取消会发生什么

输入持久保存后才返回接收确认（ACK）。确认只证明收到输入，不证明任务完成或工具副作用只发生一次。无响应和断线也不能证明调用没有执行，未知结果不允许自动重跑。

断线后的快照恢复正文、计划、终态及仍存活的审批或提问入口；已答复、超时、取消或重启后失效的旧入口不能重新操作。重启不会自动续跑旧模型流，旧回合标记中断或未知。断流、取消或连接异常结束前已接收的正文保留为未完成消息。

无附件的“继续”进入原任务的恢复操作，沿原目标和计划继续，补充要求追加到原目标。是否可恢复由运行时判定，显式取消的任务拒绝继续。
目标模式只属于“这一个目标”，不是会话的永久模式。它由 `/goal <任务>`（或目标入口）显式开启，或由模型在普通回合中明确声明“这是需要做到完成的执行工作”（有具体交付物、需要跟踪或验收）而开启。任何模式下，权限允许的工具面都保持完整；目标契约只额外提供进度、`update_goal` 终态、完成验收和失败恢复。

目标生命周期、消息归属和执行模式是三个不同的事实，不能由一个字段隐式推断：

- **目标生命周期**（`goals.state` 与 `sessions.outcome`）：目标是否仍欠工作、能否再进入。欠工作与“能否恢复”由同一个可恢复性判定决定；阻断（`Blocked`）、可恢复失败、中断和预算边界都让目标保持欠工作，交付完成或用户显式取消才结清。
- **消息归属**：新消息是普通对话、原目标的继续，还是显式的新目标。继续进入的是原目标的持久身份；`/goal <任务>` 是唯一从任意消息显式建立新目标的方式。
- **执行模式**（`sessions.collaboration`）：本次回合使用普通对话还是目标执行。目标是“这一个目标”的执行窗口，不是会话的永久模式。

目标窗口结束时，路由与终态事实在同一次提交中一起结束：窗口关闭（交付、阻断、失败或取消）后，后续普通消息回到普通对话，客户端也会收到通知，不会继续显示运行时不存在的目标状态。被打断或被预算中断的窗口只是暂停，仍保留路由，用户补充的话继续同一个目标。以目标轴创建、但窗口中从未打开目标（例如只做分发的并行父会话）的会话保留其声明轴：之后的消息在那里是新目标的声明，而不是对没人执行过的工作的继续。

区分这些事实是必需的，因为“目标仍欠工作”不等于“下一条消息必须进入目标执行”。阻断后用户问“为什么没有权限”是对模型的追问，不是新的执行委托：它按普通对话作答，原目标的身份、objective 和恢复能力都不受影响；之后的“继续”按身份恢复同一个目标。任何普通消息都不会把目标路由的残留变成新目标，也不由消息长度、关键词、工具数量或轮次决定。普通回合中模型显式声明执行工作时，若该任务已经欠着一个目标，声明加入那个既有身份，而不是再开一个。

### 停止当前回合和取消任务

| 动作 | 后续行为 |
| --- | --- |
| 停止当前回合（`CancelCurrentTurn`） | 中断当前回合，保留可恢复任务 |
| 取消整个任务（`CancelTask`） | 保存已取消结果，结清目标，并拒绝之后继续 |

取消经历请求、送达、执行终止和终态持久提交。回合还活着时显示“正在停止”，提交终态后才能显示“已停止”。持久取消先于完成提交时，结果必须为已取消；已提交的完成不被迟到取消覆盖。

### 多客户端同时改设置

标题、模型、权限、思考选项和协作方式等设置，按客户端实际看到的日志版本更新。别人已修改时，本次冲突会明确报错并刷新，不能自动拿新版本覆盖。

## 7. 后台命令与多智能体

后台进程从启动时明确寿命，不根据界面是否打开猜测。

| 生命周期 | 何时停止 |
| --- | --- |
| 随目标（`goal`，默认） | 创建它的目标结束时回收 |
| 随运行时（`runtime`） | 不随目标结束清理，当前运行时退出时回收 |
| 随会话（`session`） | 由独立执行宿主托管，显式删除创建会话时停止 |
| 持续运行（`persistent`） | 用于跨运行时重启运行的服务，自行结束或显式停止时结束 |

运行时更新不会停止已托管服务。无法确认进程身份时显示未知或需要人工恢复，保留其未结算的写入归属，不向可能已被其他程序复用的进程号发送信号。

日志有容量上限，客户端读取慢时仍持续读取进程输出；丢弃内容会明确标记截断。命令及其所有子进程都结束后，才统计和结算文件变化。

### 子智能体共用哪些约束

产品已有探索、执行和评审等子智能体角色，支持父子会话，也支持项目或用户定义的 Agent。角色不同仍共用任务生命周期、所有权、写入范围、能力、取消、结算和持久化，不能建立第二套写入、权限或任务记录。自动委派由模型选择，不保证一定更快或便宜。

声明式 Agent 使用 `.leveler/agents/<name>/agent.yaml` 与 `instructions.md`，定义只能收窄现有能力类，不能新增运行时角色；创建子智能体时保存定义快照，重启仍按该快照运行。完整用法见[自定义 Agent](AGENT_EXTENSIBILITY.zh-CN.md)。

技能（Skill）是由 `SKILL.md` 和可选脚本、参考资料组成的知识包，目录名是唯一名称。项目定义优先于用户定义，用户优先于内置定义；被覆盖定义仍可诊断。兼容 Skill 直接读取原目录，索引仅有名称、范围和描述，正文按需加载。

## 8. 模型、上下文和数据

不同模型在同一套领域规则与运行时上工作。差异用明确能力表达，包括上下文窗口、思考支持、并行工具、图片、结构化输出、工具调用和最大输出，不靠模型名称猜行为。模型真实缺能力时明确报告，不用隐藏行为假装支持。

模型负责理解、规划、工具选择、调试和证据判断。运行时修复并发、取消、恢复、权限和一致性等工程问题，不替较弱模型规划。领域层可以根据重复验证、长期无有效进展或重复失败等可观察行为提供反馈；所有自适应策略必须可观察、解释、关闭、度量且与模型身份无关。这不是为了拉平不同模型的能力，而是为了让每个模型的能力进步直接转化为更好的实际任务表现。

### 模型读到的上下文

当前契约、项目规则、选中技能、记忆与执行状态每次请求重新组装。真实用户输入、模型输出、工具调用和结果构成对话转录。两者来源和用途分开，工具或附件中的命令式文字仍是待分析数据，不能自动取得项目或用户指令权限。

项目规则投递是宿主契约，不由模型决定。项目 `.leveler/config.yaml` 声明哪些章节是强制规则；运行时先投递全部强制章节，再按文档顺序填充可选章节，所有规则文档共享每个请求唯一一份字节预算。规则文本排在仓库文件清单之前，但权威等级不变，位置不提升权限。未投递内容在提示中按来源、章节 id 与标题点名；强制章节放不下时明确报告，不静默丢弃。`read_project_rules` 只是同一 loader 上的可选查询，任何强制规则都不依赖模型是否调用它。

事实的含义由模型或人给出，运行时不得从自然语言推断。运行时可以解析协议、精确 CLI 语法、路径、结构化值、证据 ID、退出码、权限规则和凭据形态；不得用中英文主题词表、停用词表、同义词映射、句式、连接词或文本相似度决定身份、等价、因果、适用条件或两条事实是否同一条。`./dev arch` 检查这类结构，所有例外必须在 `docs/ARCHITECTURE_GUARD.exceptions` 记录理由、Owner 和测试。门禁是结构筛查，不替代代码评审对语义的判断。

长历史超过实际请求阈值时，系统保留目标、规则与最近工作集，将中段替换为模型写的简报。简报可能有遗漏，属于建议性上下文；原始转录保留。摘要不可用时明确说明细节不可用。

协议要求的历史推理回传同样由事实决定，而不是由哪个入口写了配置决定。优先级固定为：模型族的线协议能力、用户显式声明、保守默认值（不回传）。显式声明可以加强默认要求，也可以在一个部署明确关闭了保留式思考时退出该模型族的默认回传；不能削弱供应商的硬性要求。削弱硬性请求（DeepSeek 带工具、Kimi K2.7+/K3 任意请求）在启动时以模型和字段名报错，而不是等到请求被供应商以 400 拒绝。`leveler login`、手写配置、实验室、狗粮和所有客户端走同一解析，且登录生成的配置不再写这些协议字段：用户不需要理解 Reasoning Replay 就能得到正确的模型行为。

回放范围跟着实际模式走，而不是一个固定值。DeepSeek 以“请求是否携带 `tools`”为触发条件（不是历史回合的 `tool_calls` 数量；不带 `tools` 时服务端忽略该字段）。GLM 在路由声明保留式思考期间，每次跨历史请求都必须完整回传推理链，不带工具也一样；部署明确关闭保留式思考时只保留文档要求的工具循环默认值，并可显式退出。Kimi K2.7 Code 及之后的 K2.8/K3/K3.1 思考与保留均为无条件，每个请求都回传完整 assistant 消息，且不发送 `thinking` 参数。K2.7 以下的 Kimi id 故意不在表内，因为产品已不再支持。没有任何历史推理通道的模型族不回传任何字段。

历史推理只在它真正属于当前模型时才回放。每条 assistant 回合记录产生它的路由（provider 别名、线上 model id、协议、已知时的部署地址）；同一模型经不同网关访问是两个路由。理由很直接：`reasoning_content` 没有签名，把 A 模型的私有推理交给 B 模型，等于让 B 读到一段自己没说过的话，既消耗上下文又可能误导判断。切换模型时，用户目标、assistant 正文、工具调用与工具结果都保留，只有不属于新模型的推理被丢弃；协议要求该字段存在时，发送合法的空值而不是冒充完整内容。缺失、空和未知是三种不同事实：本路由完成但没产生推理是“空”，旧会话没有记录来源是“未知”，流中断的内容永远不会被提升为完整回合。模型能力同样按事实表达：保留式思考（如 GLM 的 `clear_thinking: false`）按路由声明发送，无法关闭思考的路由不提供 `off`。

消耗包括每次模型尝试、失败、重试、压缩摘要和子任务。没有用量报告或价格信息不等于免费。子任务和 `/develop` 阶段共享父任务剩余预算；预算只能阻止后续调用，不能撤销已发生消耗。

### 数据会发到哪里

CodeLeveler 默认不向项目方或中心服务收集、上报产品遥测和用户工作数据，包括源码、文件内容、会话、提示词、模型输出、命令输出、环境、用量和崩溃上下文。

用户启用的模型服务、MCP 外部工具连接、网页搜索、远程执行或更新检查仍可能联网。每次出站由明确功能触发，目的地与用途可解释，只发送必要数据，不通过隐藏替代路径扩大范围，也不把秘密当遥测。

## 技术说明

以下说明架构责任划分与产品契约，供开发与排障参考。

### 责任划分与依赖方向

| 组件 | 唯一负责的事情 | 不能接管的事情 |
| --- | --- | --- |
| 模型 | 理解、推理、规划、选择工具与判断证据 | 文件系统、进程或任务生命周期 |
| 领域适配层（Harness） | 领域词汇、约束、工具面、上下文、协作及完成语义 | 通用生命周期、持久化、权限或隐藏推理 |
| 内核（Agent Kernel） | 模型与工具循环、流式输出、预算、usage、重试、超时和取消 | 编程、评审、仓库工作流、产品提示词和用户验收 |
| 引擎（Engine） | 会话、任务、回合、事件、恢复、后台父子关系、所有权和结果 | 领域规划与语义完成判断 |
| 能力（Capability） | 可复用执行逻辑、必要状态、生命周期与一致性 | 某个工具或产品的展示逻辑 |
| 工具（Tool） | 模型意图入口、参数解码、调用能力和表达结果或错误 | 全局状态、服务发现、权限裁决或进程生命周期 |
| 宿主执行权威（Host Authority） | 唯一执行真实文件、进程、网络副作用及权限边界 | 领域完成判断或根据 UI 改事实 |
| 持久化（Persistence） | 任务、回合、所有权、证据、用量、产物和后台工作的唯一事实源 | 竞争性重复记录 |
| 模型接入层（Provider / Protocol） | 请求响应、流、工具协议、reasoning、结构化输出、视觉和能力限制 | 改领域语义或为特定模型注入隐藏行为 |
| 产品与客户端 | 交互、导航、能力组合及本地显示状态 | 创造终态或绕过运行时管理长期任务 |

依赖从产品经领域层朝运行时、能力与基础层发展。运行时不依赖具体领域，领域层不依赖具体界面，基础层不知道编程和评审，能力不反向依赖调用它的工具。改变职责不能削弱机械正确性、安全、持久化、取消、恢复或一致性。

能力是一种职责，不要求拆成独立包或进程。新包、trait、manager、registry 或框架需要两个真实实现或消费者、依赖倒置、独立安全/协议/持久化/生命周期/远程部署边界，或已观察到的耦合问题。本地、远程和云端后端可以更换执行位置，但不能改领域语义或绕过统一权威。

### 9.0 Permission Mode 顶层产品契约

`FullAccess`（Full）在执行前放开一切：跳过权限规则、审批、sandbox、资源范围、凭据过滤和任务所有权限制。文件、外部路径、HOME、凭据、任意 Git remote、回环/局域网/互联网、进程控制和已实现的未来能力都不产生权限询问或拒绝，审批次数为 0。能力缺失、工具参数无效、操作系统或外部服务失败仍如实失败。取消、超时、持久化和资源回收仍归运行时。Full 放开的是权限判定，不是工具面披露：所有已实现能力都可使用且启用无需批准，可选工具包仍可按需进入本会话的请求面，模型不会因此失去任何工具。

`Assisted`（Auto）允许普通读写、构建、测试、访问 localhost、操作自有任务和全部 Git 操作，只在三类边界询问：

| 边界 | 例子 |
| --- | --- |
| 删除 | 绝对路径、`..`、`~`、变量或通配符的 `rm` / `rmdir`；`dd`、`mkfs`、关机。工作区内字面相对路径直接执行 |
| 提权 | `sudo` / `su` / `doas`、打开宿主应用、MCP、跨会话任务控制、Agent / 技能 / 记忆定义 |
| 安全 | 凭据明文、目的地存有凭据的 Git remote、工作区外写入、会执行本地程序的 Git 配置或参数 |

批准冻结在本次明确动作上，执行层不再次拒绝同一动作，也不扩大到之后未批准的调用。

**隔离不能比权限策略更严。** 权限层判定允许时，执行阶段不能用静默拒绝回答同一能力。确实无法进入隔离的能力，由权限层明确询问或给出结构化理由，而不是让调用方看到裸的操作系统错误。

`RequestApproval`（Restricted）使用目的地和资源边界：描述目标地址并校验每次重定向，分类本身不算执行证据。无法可靠约束的范围明确询问、拒绝或标记 Unsupported，永不静默扩权。

当前进程网络支持：macOS 在 `None` 下拒绝网络，回环为部分支持（仅规范 `127.0.0.1` / `::1` 出站，不开放监听）。Linux 与 Windows 的受限网络范围标记为不支持。`Internet` 与 Full 保持开放网络。资源授权与凭据隔离只约束 Auto 与 Restricted，不向 Full 或已批准动作添加拦截。

### 持久化与结算边界

输入、所有权和行动意图先持久化，再让它们授权的工作变得可见或不可逆。崩溃可以丢掉未来，不能丢掉已准入的过去。

回合在模型调用前持久准入：重复的客户端请求匹配到同一回合，而不是执行两次；结果未知时不自动重跑。取消分为请求、送达、执行终止和终态提交四段事实，只有终态才显示为已停止。

任务终态只有一份权威记录。已回答、声明完成、工具成功和最终正文各自证明不同的事，都不能替代终态。权威终态提交后，产品立即公布；只有已绑定具体任务与运行记录的后台收尾可以继续，但不能延迟结果。

### 数据边界

网络访问是真实宿主副作用，因此数据出站遵循同一执行权威和最少必要数据原则。产品遥测和用户工作数据默认不上报；用户明确启用的外部能力只能发起该能力所需的数据出站，目的地和用途可解释，不通过隐藏替代路径扩大范围，也不把凭据或秘密当遥测。

### 后续演进与当前范围

父子智能体、角色协作和声明式 Agent 已存在。未来增加评审、研究等独立领域，应复用同一运行基础。工作区、执行、浏览器、搜索、记忆、版本控制、代码理解、媒体和外部服务可以继续成为多领域共享能力。

长期方向包括远程主机、容器、隔离虚拟机与云端 Worker，以及长目标、暂停继续、后台执行、跨设备续接、持久子会话和长期上下文。这里记录演进方向，不能据此宣称未交付产品或平台已可用。
