# C2.1 CONTEXT COST ATTRIBUTION REPORT

日期：2026-08-08。分支 `feat/coding-real-task-completion-c1`。模型 `deepseek/deepseek-v4-flash`。

**本轮 MEASURE ONLY：零生产代码改动**（`git status` 全程只有一个新增的离线分析脚本 `scripts/analyze_context.py`）。未修改 prompt、compaction 参数、drive policy、工具描述、工具输出裁剪、repo map、verifier、runtime。未启用任何 ablation。

**要回答的问题：真实仓每轮多出来的几十 K token 到底去了哪里？**

答案：**不是被重复搬运的，是被无限累积的 `read_file` 结果。** 真实仓最后一轮的请求里，读取结果占 57%（yq）到 72%（ripgrep）；其中 89.7%（ripgrep）的内容既不属于系统提示也不属于最近 12 条消息 —— 它是一轮都没被回收过的旧读取输出。轮内唯一的压缩闸门设在 524,288 token，比实测最大值高 5 倍，因此从未触发。

---

## 1. 方法

数据源是引擎自己持久化的 `EngineEvent::ContextSnapshot`，它逐轮记录**发给模型的完整消息列表**，加上 `model_requests` 表里 provider 实际计费的 `input_tokens`。没有重跑任何 case，没有调用任何模型，没有靠文本猜来源 —— 每条 `tool_result` 通过 `call_id` 精确回连到 `tool_call_started` 事件的工具名与参数。

token 计数**复刻产品自己的估算器**（`leveler-agent/src/compaction.rs`）：`ascii_bytes/4 + wide_bytes/3`，图片按 `IMAGE_BYTE_EQUIV/4` 计。用同一个函数意味着这里的数字就是 compaction 会看到的数字。

分析脚本：`scripts/analyze_context.py`（只读、离线、可复算）。

**测量学发现（重要）**：扣掉 schema 常数后，provider 计费是产品估算器的 **1.19×（Rust 源码）到 1.28×（Go 源码）**。也就是说 `estimate_tokens` 对源码**系统性低估 16–22%**。所有以该估算器为单位表达的阈值（24k 的 transcript 折叠阈值、524k 的轮内预算、单工具输出上限）实际都比设计意图**晚 20–28% 才触发**。本轮不修，记为 C2.2 候选。

## 8. Compaction Wiring Audit（只审计，不修）

**A. 哪条 execution path 实际调用 auto-compaction？**

存在**两条互不相同**的路径：

| | 轮内（intra-turn） | 跨轮（cross-turn） |
| --- | --- | --- |
| 位置 | `leveler-agent/src/executor/drive.rs:2235` | `RawTranscript::assemble` → `budget_prior_messages`（`engine.rs:178`） |
| 触发条件 | `max(provider used_tokens, estimate_tokens(messages)) > policy.context_budget` 且 `context_budget > 0` 且还有下一轮 | `estimate_tokens(raw) > threshold` |
| 阈值来源 | `policy.context_budget` = `ExecutionPolicyResolver` → `profile.limits.reliable_context` | 常量 `PRE_REQUEST_COMPACT_THRESHOLD = 24_000` |
| 本次实际值 | **524,288**（`configs/models/deepseek-v4-flash.yaml`） | 24,000 |
| 作用对象 | 本轮将要发出的完整消息列表 | 数据库里已存的 transcript |

**B. Eval / direct tool loop 是否走这条路径？**

走的是**任务路径**：`eval_cmd.rs:676` → `engine.create_task(&spec)` → `engine.rs:839` 的 `assemble(..., PRE_REQUEST_COMPACT_THRESHOLD)`。但 **eval 每个 case 都是全新 session，`raw` 在任务开始时为空**，所以 24k 折叠**一次都不会命中**。随后 48 / 100 轮全部发生在**同一次 drive 循环内部**，只受 524,288 约束。

**C. 24k 阈值作用于完整 request 还是 transcript estimate？**

作用于 **transcript estimate**（`budget_prior_messages` 的 `estimate_tokens(&raw)`，只含已存消息，不含系统提示、不含工具 schema）。轮内那条 524k 阈值才作用于**完整 request 的近似**：取 `provider 上一次报告的 used_tokens` 与 `本轮完整消息列表估算` 的较大者 —— 但同样不含工具 schema。

**D. 为什么 provider input >40k / >90k 仍没有 compaction？**

因为它们离阈值差得远：ripgrep 最大 126,145（provider）/ 100,714（本地估算），阈值 524,288 —— **只到 19–24%**。24k 那条根本不在这条执行路径上。全程 `Compacted` 事件数 = 0，与实测一致。

**E. 这是设计如此，还是某条 execution path 没接上？**

**是设计如此，不是 wiring bug。** 两条路径都正确接线、都有测试覆盖（`loop_test.rs:1537` 用 `with_context_budget(1000)` 锁定轮内压缩确实会触发）。

但设计里有一个**真实的空洞**，本轮的数据把它照出来了：

1. **轮内在 0 与 `reliable_context` 之间没有任何回收机制。** 一次长任务可以在单轮内累积 100k+ 的陈旧读取输出，直到撞上 524k 悬崖才第一次整体折叠 —— 而实测中根本撞不到。
2. **两条路径的阈值差 21.8 倍**（24k vs 524k），单位口径也不同（transcript vs 完整请求）。跨轮对 24k 就折叠，轮内到 100k 也不动。
3. **估算器低估 16–22%（§3）**，两条阈值实际都比设计意图晚触发。

三项记为 C2.2 candidate。**C2.1 不修。**

## 10. Context Duplication

分两个口径量：

**(a) 逐字节完全相同的工具结果重复搬运**：

| Run | 工具结果 token | 字节级重复 | 占比 |
| --- | ---: | ---: | ---: |
| MF1 | 1,559 | 145 | 9.3% |
| yq | 26,768 | 50 | **0.2%** |
| ripgrep | 84,767 | 115 | **0.1%** |

**几乎为零。上下文里没有"同一段内容被搬运两遍"的问题。**

**(b) 同一路径被反复读取（内容不同但信息重叠）** —— 这才是真正的冗余：

| Run | 读取 token | 被后续读取取代的旧读取 | **严格无损冗余** |
| --- | ---: | ---: | ---: |
| EDIT1 | 287 | 0 | 0 |
| EXP1 | 2,546 | 0 | 0 |
| MF1 | 1,043 | 174 (16.7%) | 0 |
| yq | 21,198 | 58 (0.3%) | **1,462 (6.9%)** |
| ripgrep | 72,700 | 36,956 (50.8%) | **16,842 (23.2%)** |

"严格无损冗余"的定义很窄：**该次读取的内容已被同一路径更早一次仍驻留的整文件读取完全覆盖，且两次读取之间该路径没有被编辑过。** 丢掉它零信息损失。ripgrep 的 16,842 token 里，14,500 来自 `crates/core/flags/defs.rs` —— 这个 14.5k token 的文件被**整文件读了两次**。

**结论：问题不是"重复搬运"（0.1–0.2%），是"陈旧累积"。** 真正的浪费是读进来后再没有任何机制判断它是否还需要。

## 11. Localization Commitment（只分析，不产品化）

C1.5A 已实证 nudge 的因果效应（first edit 提前 35–44%、pre-edit 轮数降低 38–46%）。从本轮的上下文成本视角追加一条**新的**观察：

ripgrep 的 `first_relevant_file_round = 3`、`first_edit_round = 45`。第 10 轮时读取结果已达 39,131 token —— **在真正开始编辑之前，上下文的大头就已经被灌满了**。也就是说 localization commitment 的收益不止是"少跑几轮"，它直接决定了**后续每一轮要背多重的包袱**：第 45 轮才开始编辑，意味着后面 55 轮每一轮都要重发这 39.1k 探索期读取内容。

按 ripgrep 的 provider 计费粗算：若编辑提前到第 20 轮左右并对应减少探索期读取，节省量在同一数量级。

**本轮不产品化，不默认启用。** 记录为 C2.2 的次优候选。

## 13. C2.2 RECOMMENDED TOP-1

> **轮内读取结果的生命周期管理（Read-Result Lifecycle in the drive loop）**

按 (path, 覆盖区间, 修改水位) 为每次读取结果建立标识，在组装下一轮请求时：先做**严格无损去重**（内容已被同路径更早一次仍驻留的读取完全覆盖，且其间该路径未被编辑 → 丢弃），再做**取代式回收**（同一路径存在更新读取时，回收旧版本）。

**为什么是它 —— 由数字决定，不是由直觉决定：**

1. 它是最大的桶：ripgrep 最终请求的 **72.2%**、yq 的 **57.4%**，其余所有桶加起来都不到它一半。
2. 它有一个**零信息损失的下界**：ripgrep **16,842 token（读取量 23.2%、整个请求 16.7%）**、yq **1,462 token**，丢掉不损失任何信息。这不是估计，是逐 call_id 按覆盖关系与编辑水位算出来的。
3. 它有一个明确上界：取代式回收可再释放至 **50.8%** 的读取量（ripgrep 36,956 token）。
4. 它随任务长度增长而增长 —— 排名 #2 / #3 是每轮常数，随轮数线性增加但**占比递减**；#1 是**占比递增**的那一个，恰好在最难的任务上最贵。
5. 排除项已经排干净：不是重复搬运（0.1%）、不是项目上下文（0）、不是 compaction 没接线（接线正确）。剩下的唯一解释就是陈旧累积。

**明确不推荐为 TOP-1 的：**

- **工具 schema 渐进披露**（已有 `expand_tools` 工具作为抓手）：yq 全程 14% 的计费确实可观，但它在最后一轮的**边际**成本只占 9.9%，且不解决 #1；留作 C2.3 候选。
- **压缩系统提示**：属于产品行为改动，收益固定且封顶，且 §7 证明它没有隐藏膨胀。
- **降低 `reliable_context`（让 524k 闸门更早触发）**：这是钝器。它会在到达阈值时一次性折叠整个历史（含仍在用的 4%），而 #1 能精确回收陈旧部分。
- **Localization commitment 默认启用**：C1.5A 已证因果、§11 也给了上下文视角的佐证，但它是**减少读取的产生**，不是**回收已产生的读取**；两者不冲突，且 #1 的收益不依赖模型行为改变。

**C2.1 不实现 C2.2。**
