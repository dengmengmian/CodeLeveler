# Tool Surface Baseline — T0

Foundation Hardening stage T0. Establishes what the model can see, what it
actually called, and freezes the A/B contracts that decide which tools stay on
the default model surface.

```text
architecture HEAD   e623f531f6e690c789a30291e1cd04a52138191d
generated by        evals/scripts/tool_surface_baseline.py
artifacts           baseline.txt   full inventory and usage tables
                    raw.json       per-call rows, project and session ids hashed
```

No runtime instrumentation was added for this. Every number comes from facts
the runtime already persists: the `tool_call_started` / `tool_call_finished`
events in each session database, and the `sessions` / `model_requests` tables
beside them. Metrics the EventLog cannot answer are listed as gaps in §5
rather than estimated.

## 1. What the model sees

| Surface | Count |
| --- | --- |
| `core_registry()` | 14 |
| `full_registry()` — **the default** | 43 |
| Executor-injected control tools | 7 |

Confirmed against the architecture document; the numbers have not moved.

Two defects in `expand_tools` fall out of the same parse:

- It advertises `mcp` and `subagent` as categories, but
  `expand_tool_category` registers nothing for either. Requesting them is a
  guaranteed no-op.
- It handles `browser` but does not advertise it. The model cannot ask for the
  one category it would actually unlock.

## 2. The evidence set, and what it cannot support

94 session databases under `LEVELER_HOME`, 99 sessions, 1725 tool calls.

| Class | Sessions | Tool calls | Window |
| --- | --- | --- | --- |
| REAL | 5 | 559 | 2026-08-28 .. 08-31 |
| DOGFOOD | 3 | 28 | 2026-09-08 .. 09-10 |
| EVAL | 91 | 1138 | 2026-09-08 .. 09-09 |

**Read these limits before reading any conclusion below.**

- **One model, one profile.** Every session in every class ran
  `deepseek/deepseek-v4-flash` on the `balanced` profile. There is no weak /
  strong split in this data, so "does `replace` disproportionately help weaker
  models" **cannot be answered from it**. That is the whole reason A/B-REPLACE
  exists in §6.
- **`balanced` means `full_registry()`.** No session in this set ran the
  economy surface, so there is no evidence about `core_registry()` in use, and
  none about whether a smaller surface changes behavior.
- **The REAL window is ten days stale and predates the current tool set.** All
  559 REAL calls are from late August. One of them names `resolve_finding`, a
  tool that does not exist at this HEAD. Real usage since 2026-09-08 is 28
  calls total.
- **EVAL is not user behavior.** Fixture repositories, scripted goals, a task
  shape the harness chose. It says what the tools do under a synthetic load,
  not what a person's work needs.

Sample sizes this small do not settle anything on their own. They are strong
enough to reject a claim, and too weak to establish one.

## 3. The headline result

**29 of the 43 default-visible tools were never called in real use. 32 of 43
were never called in evaluation.**

Real use touched 16 distinct names; two of those (`resolve_finding`) do not
exist at this HEAD. Evaluation touched 14, two of which
(`git_log`, `git log`) were hallucinated and errored.

Every one of the six focus candidates has a call count of zero, in both
classes, except one call of `expand_tools` that failed:

| Candidate | REAL + DOGFOOD | EVAL |
| --- | --- | --- |
| `replace` | 0 | 0 |
| `read_symbol` | 0 | 0 |
| `blast_radius` | 0 | 0 |
| `expand_tools` | 1 (error) | 0 |
| `create_checkpoint` | 0 | 0 |
| `restore_checkpoint` | 0 | 0 |

The zeroes extend past the focus list: `find_symbol`, `find_references`,
`diagnostics`, all 12 browser tools, `memory`, `remember`, `forget`,
`consolidate_memory`, `load_skill`, `create_skill`, `view_image`,
`web_search` and `web_fetch` are all zero in both classes.

**A zero is not by itself a verdict.** A capability can be unused because the
tasks in this window did not need it, because the prompt never suggested it,
or because the model does not reach for it. Those have different remedies —
removal, prompting, or surface composition — and this data does not separate
them. What the zeroes do establish is that the cost of the default surface is
being paid on every round for tools that are not earning it here.

## 4. What the calls that did happen show

### 4.1 `expand_tools` failed the only time it was used

A child agent requested `["shell", "command"]`. Neither is a category. The
tool refused and listed the real ones. The capability the agent wanted
(`shell_command`) was already on its surface.

That single call reproduces the whole argument in `docs/ARCHITECTURE.md` §6.4:
the model does not know what the categories are, and asking it to manage its
own tool surface spends a round to discover that.

### 4.2 `apply_patch` failures were never rescued by `replace`

Six edit calls failed. Four were `failed to apply hunk: could not find
expected lines` — exactly the failure `replace` exists to absorb. In every
case the model retried `apply_patch` instead:

```text
apply_patch fails → apply_patch, update_goal          3
apply_patch fails → apply_patch, run_command, ...     2
apply_patch fails → apply_patch, read_file, ...       1
```

`replace` sat on the surface, unused, through the precise failure it was
built for. On this model, on this data, it is paying schema cost and returning
nothing. Whether that holds for a weaker model is what A/B-REPLACE has to
answer.

### 4.3 The error rates need reading, not quoting

| Tool | Errors / calls | What they are |
| --- | --- | --- |
| `wait_task` | 26 / 57 | 20 are `wait timed out` or `wait cancelled` — designed behavior, not failure |
| `run_command` | 23 / 127 | Non-zero exits from real commands, plus 300s/600s timeouts |
| `read_file` | 21 / 623 | 19 are `file not found` on a guessed path |
| `get_task` | 4 / 45 | All four passed an agent id where a task id belongs |
| `shell_command` | 13 / 193 | Two denied by the user; the rest real command failures |

Two of these are interface defects rather than tool failures. `wait_task`
reports a timeout as `is_error`, which makes every dataset that counts errors
overstate its failure rate — including this one, before the breakdown. And
`get_task` failing four times out of four on an agent id says the id spaces
are confusable at the model-facing boundary.

### 4.4 Latency, with a caveat

Wall time here spans admission, any approval wait and in-batch scheduling. It
is an upper bound on execution, not a measurement of it.

| Tool | p50 | p95 | max |
| --- | --- | --- | --- |
| `read_file` | 2 ms | 14 ms | 116.8 s |
| `grep` | 18 ms | 58 ms | 148.5 s |
| `apply_patch` | 11 ms | 29 ms | 120 ms |
| `run_command` | 1597 ms | 120 s | 600 s |
| `wait_task` | 120 s | 600 s | 900 s |

Twelve read/search calls exceeded one second. The slowest `read_file` took
116.8 seconds on a single markdown file. That is consistent with the
full-file scan described in `docs/ARCHITECTURE.md` §18.3.A, but the
measurement cannot prove the scan caused it — the same span includes
scheduling. Attributing it needs execution timing the EventLog does not carry
(§5).

## 5. Measurement gaps

Recorded, not worked around. **Do not add telemetry to close these before the
A/B contracts need it** — each one should be closed by the cheapest thing that
answers the specific question, and some do not need closing at all.

```text
MEASUREMENT_GAP  per-tool token attribution
    model_requests records tokens per request, not per tool call. Claims of
    the form "this tool saves N tokens" cannot be made from this data.

MEASUREMENT_GAP  tool execution time
    Only admission-to-result wall time is persisted. Time inside the tool is
    not separable from approval waits and in-batch scheduling.

MEASUREMENT_GAP  model capability tier
    Every session used one model. Nothing here speaks to weak-model behavior.

MEASUREMENT_GAP  tool surface actually advertised per round
    The registry composition is known statically, but no event records which
    definitions a given round sent. After an expand_tools call the live
    surface differs from full_registry() and the log does not say how.

MEASUREMENT_GAP  checkpoint provenance
    Runtime checkpoints and model-requested checkpoints are not distinguished
    in the event stream. With zero model-facing calls this is moot today; it
    would matter if A/B-MODEL-CHECKPOINTS ever ran with non-zero usage.
```

## 6. Frozen A/B contracts

These are the contracts stage T1 executes. They are frozen here so the
question cannot drift after the numbers arrive.

Shared rules:

- **Control is the current default**, treatment is the change. Never the
  reverse.
- **Arms interleave.** Provider latency has moved between days before
  (`docs/ARCHITECTURE.md` is not the record for that; the eval methodology
  is). Sequential arms are void.
- **A tool is removed only on evidence**, and never because another tool could
  theoretically reproduce it.
- **Safety guard, all contracts**: no arm may weaken permission, approval,
  sandboxing, write scope, stale-write protection, CAS, rollback or recovery.
  An arm that changes any of those is invalid, not interesting.
- **Null result rule**: if the primary metric does not move outside the
  interval, the tool loses its default-surface slot. The burden is on the tool
  to earn the round cost it imposes, not on the removal to prove harm.

### A/B-REPLACE

```text
question    Does exact find/replace rescue patch-context failures, and does it
            help weaker models more than strong ones?
control     apply_patch only on the model surface
treatment   apply_patch + replace (current default)
task set    edit-heavy cases with non-trivial context matching; include the
            four EVAL cases that produced "could not find expected lines"
model       at least two tiers. One model is not a valid run of this contract.
reps        >= 6 per (arm x model), interleaved
primary     task success rate
secondary   edit retries, invalid-patch count, rounds, tokens, wall time
guard       no change to the write path, CAS or stale-write protection
```

This is the one contract whose current answer is *not* "remove". Zero usage on
one strong model is not evidence about the weak-model case that motivates the
tool.

### A/B-READ-SYMBOL

```text
question    Does read_symbol reduce rounds or output versus find_symbol
            followed by read_file?
control     no read_symbol on the surface
treatment   read_symbol present
task set    symbol-navigation tasks in a repository with a working language
            server; verify the LSP path is live before scoring
model       one tier is acceptable; note it
reps        >= 6 per arm, interleaved
primary     rounds to first correct edit
secondary   tool calls per task, result bytes, search retries, task success
guard       none beyond the shared rules
```

Prerequisite: zero calls in this baseline may mean the model does not reach
for it, or that the LSP session never came up. Establish which before
scoring, or the run measures nothing.

### A/B-BLAST-RADIUS

```text
question    Does blast_radius change the edits that follow it, in a way
            find_references plus grep does not?
control     blast_radius absent
treatment   blast_radius present
task set    multi-site refactors with a known correct edit set
model       one tier
reps        >= 6 per arm, interleaved
primary     refactor recall — fraction of required sites edited
secondary   rounds, tokens, missed-site count, task success
guard       none beyond the shared rules
```

Score the follow-up actions, not the call count. A tool whose result does not
change the next edit has not earned its slot however often it is invoked.

### A/B-EXPAND-TOOLS

```text
question    Does model-controlled surface expansion beat harness-side
            selection on cost and success?
control     harness selects the surface; no expand_tools
treatment   economy surface + expand_tools (the pattern as designed)
task set    tasks spanning several capability categories, so expansion has
            something to buy
model       one tier
reps        >= 6 per arm, interleaved
primary     total tokens per completed task
secondary   rounds, no-op expansion rate, whether newly exposed tools were
            then used, task success
guard       none beyond the shared rules
```

Before running this, fix the two inventory defects in §1. Measuring a feature
whose category list is wrong measures the bug. Note also that this contract
carries a prior: the burden is on the dynamic option, because it is the one
that inverts surface ownership.

### A/B-MODEL-CHECKPOINTS

```text
question    Does a model-facing checkpoint tool add recovery value over the
            runtime's own checkpoints?
control     create_checkpoint / restore_checkpoint absent from the surface
treatment   both present (current default)
task set    tasks with a realistic chance of a bad edit needing rollback
model       one tier
reps        >= 6 per arm, interleaved
primary     recovered-from-bad-state rate
secondary   rounds, task success, restores without a useful preceding
            checkpoint
guard       runtime checkpoint and crash recovery are untouched in both arms.
            This contract is about the model-facing tool only.
```

With zero calls in the entire evidence set, the honest prior is that the
control arm loses nothing. Run it to confirm, or demote the tools on the
zeroes and skip the run.

## 7. What T0 does not decide

No tool was removed, demoted, or changed. No registry, context, kernel,
engine, permission or sandbox behavior was touched. The default surface is
still `full_registry()`.

T0's output is this baseline, the script that regenerates it, and the five
contracts above. T1 runs the contracts.

Two fixes are worth doing before T1, and neither needs a contract, because
both are defects rather than judgement calls: the `expand_tools` category list
(§1), and `wait_task` reporting a designed timeout as an error (§4.3).
