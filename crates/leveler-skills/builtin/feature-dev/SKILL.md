---
name: feature-dev
description: 分阶段实现一个新功能：先摸清现状和需求，再设计、实现、评审，而不是直接开写。适用于"加个 X 功能"这类需要动多处代码的需求。
---

一个新功能直接开写，代价通常不是写错，而是**写完才发现方向不对**——重复了已有实现、绕过了既有约定、或者做的根本不是用户要的那件事。

这个流程用几分钟的前置调查换掉那种返工。**不要跳阶段**，但也**不要机械走完**：需求本身很小的时候，明说"这个不需要走完整流程"然后直接做。

三个可复用的 agent 已经内置，用 `spawn_agent` 的 `agent` 参数调用，**不要把 persona 重新贴进 `task`**：

| agent | 用在 | 作用 |
|---|---|---|
| `code-explorer` | 阶段 2 | 沿真实执行路径摸清现有实现 |
| `code-architect` | 阶段 4 | 依既有惯例出方案 |
| `code-reviewer` | 阶段 6 | 审正确性/安全/规范 |

**同一轮发多个 `spawn_agent` 调用即并行。** 相互独立的调查/评审面要一次发出去，不要串行。

---

## 阶段 1 · 需求澄清

先想清楚要做的到底是什么，再动手查。

- 用户要解决的问题是什么（不是"要什么功能"，是"为什么要"）
- 什么算做完
- 明确的边界：这次**不**做什么

需求已经足够清楚就直接进阶段 2，不要为了走流程编问题。

## 阶段 2 · 摸清现状

按**独立的调查面**拆开，同一轮并行 spawn `code-explorer`：

```
spawn_agent(agent="code-explorer", task="查清 <模块 A> 现在怎么工作：入口、执行流程、关键文件")
spawn_agent(agent="code-explorer", task="查清 <模块 B> …")
```

拆分依据是**互不重叠的代码区域**，不是"再多派一个更保险"。只有一个调查面就只派一个，或者自己读。

汇总时明确记下：现有惯例是什么、新代码要接进哪里、有没有已经实现了一半的东西。

## 阶段 3 · 补齐认知缺口

阶段 2 通常会翻出阶段 1 想不到的问题（已有的实现和用户描述不一致、有两个地方都像入口、既有约定和需求冲突）。

**有真问题才问**，一次问完，不要挤牙膏。没有就直接进阶段 4 并说明为什么不需要问。

## 阶段 4 · 设计方案

并行 spawn `code-architect`，让它们从不同角度出方案（例如"最小改动"与"结构更干净"），然后自己做取舍。

```
spawn_agent(agent="code-architect", task="<需求> + <阶段2的发现>，给最小改动方案")
spawn_agent(agent="code-architect", task="<需求> + <阶段2的发现>，给结构更清晰的方案")
```

产出必须包含**落地顺序**：每步能独立编译、独立验证。把这个顺序写进 `update_plan`。

方案显而易见时不要硬凑两个——直接说清做法和理由。

## 阶段 5 · 实现

按阶段 4 的顺序做，**每步遵守本仓库的 TDD 规范**：先写一个会失败的测试，跑红，再写实现，跑绿。

并行只在**文件不重叠**时用：

```
spawn_agent(agent="code-explorer", role="worker", files=["src/a.rs"], task="…")
```

`role="worker"` 必须给 `files`，且并行 worker 之间的 `files` 不能有交集——两个 agent 改同一个文件会互相覆盖。拿不准就自己顺序做。

## 阶段 6 · 评审

改动完成后，并行 spawn `code-reviewer`，按**维度**分而不是按文件分：

```
spawn_agent(agent="code-reviewer", task="审 <本次改动> 的正确性与边界")
spawn_agent(agent="code-reviewer", task="审 <本次改动> 的安全性：输入校验、权限、密钥")
```

评审结果**自己判断后再改**，不要照单全收——reviewer 看不到完整上下文，可能提出超出本次范围的要求。采纳了什么、驳回了什么、为什么，都要说。

## 阶段 7 · 收尾

- 做了什么，落在哪些文件
- **验证结果**：测试跑了没有、结果是什么。没跑就直说没跑
- 已知未做的部分和原因
- 值得记的项目约定 → 用 `remember` 提议

## 不要做的

- 不要为了显得充分而派多余的 agent；每个 spawn 都要有独立的调查面
- 不要把三个内置 persona 的内容复制进 `task`——用 `agent=` 引用
- 不要在阶段 2 结束前写实现代码
- 不要在阶段 7 报告没有实际跑过的验证
